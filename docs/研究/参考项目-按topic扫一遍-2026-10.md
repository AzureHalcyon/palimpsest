# 参考项目：按 topic 扫一遍（2026-10）

> 目标项目：**palimpsest**——常驻循环 ＋ 四段分层旧摘要（band）＋ 两块原文，按事件组织记忆，
> 回忆是重写出来的，不是把原文塞回上下文。
>
> 本文回答一件事：**在 GitHub 上按 topic 能扫到谁，哪些零件比我们做得细，能把哪些直接写进 `loop/`。**
>
> 证据标注：
>
> - `[官方文档]` —— 仓库自己的 README 或 `docs/`，读到原文
> - `[源码]` —— 我读了具体代码，给 `文件` 或函数名
> - `[二手]` —— 别人的清单/描述，非仓库原文
> - `[推断]` —— 我的判断
>
> **这次没跑过任何一个仓库，也没克隆**：结论全部来自 README 与它们自带的文档，
> 凡是"跑起来会怎样"的一律 `[推断]`。取数时间 2026-10-25。
> 数字（阈值、半衰期、字数上限）都是它们文档里自己写的，我没有复算。

## 1. 怎么扫的

`topic` 是发现工具，不是分类。同一批仓库会在 `long-term-memory`、`ai-companion`、
`memory` 三个 topic 下反复出现；按星数排，前 30 名里大约 2/3 是"给 agent 加一个记忆库"，
和我们的形状根本不同。真正有用的是下面这几个 topic：

| topic | 页面前几个的样子 | 有用密度 |
|---|---|---|
| `long-term-memory` | claude-mem(102k)、mem0(67k)、agent-memory、nemori | 高：这一支在解决"压缩后怎么注入" |
| `ai-companion` | airi(50k)、Open-LLM-VTuber、ai-companion-kit、Miru、Mirrai | 中：一半是 Live2D/语音壳子，记忆部分反而薄 |
| `episodic-memory` | nemori、engrim、Cortex、kyros-ai | 中：概念对得上，工程多半很小 |
| `context-engineering` | headroom、cognee、planning-with-files | 低：多是编码 agent 的上下文压缩 |
| `proactive-agent` | N.E.K.O、awesome-proactive-agents | 高：只有"什么时候该开口"这一件事，正对着我们的缺口 |

两份清单值得留着当索引：`DasterProkio/awesome-ai-companion`（1063，11 个一级类，
其中 `Memory, Identity & Emotion State` 与 `Background Heartbeats & Proactive Messaging`
两栏最相关）与 `tao-hpu/awesome-proactive-agents`（论文级，只讲时机）。

## 2. 一句话结论

**我们这条路线上没有别人做到同样程度，但每个零件都有比我们更细的先例。**
按 topic 扫完，能借的东西集中在五处：时间感、开口闸门、睡眠期整理、上下文形状（缓存）、
重要度与反思。最该先读的两个仓库是 `tigerless-labs/agent-memory` 与 `VictorTaelin/OptMem`：
前者是"常驻＋睡觉时整理"，后者是"用一段提示词＋一棵摘要树把我们整套东西压到最小"。
按"不靠检索、把整个过去压进每次调用"这一条排，最接近我们的是
`laude-institute/headlong`（它把人发来的消息也只当成思想流里的一条 observation）。

## 3. 结构上最同构的几个

| 仓库 | 它是什么 | 与我们的差别 |
|---|---|---|
| [agent-memory](https://github.com/tigerless-labs/agent-memory) 4.7k | Markdown 为真源、SQLite 做索引、带独立的睡眠期整理层 | 它没有常驻窗口，靠宿主钩子触发；我们反过来，窗口是我们的本体 |
| [claude-mem](https://github.com/thedotmack/claude-mem) 102k | 钩子抓每次工具调用，压成 observation，下次会话注入 | 它是"跨会话记忆"，没有"在场"这个概念；我们不要会话边界 |
| [nemori](https://github.com/nemori-ai/nemori) 214 | 按事件分割理论把对话切成 topic episode，再提炼语义记忆 | 它是检索库，没有上下文拼装；我们的 band 就是它的 episode 链 |
| [headlong](https://github.com/laude-institute/headlong) 1.2k | 约 11K 行 Bash 的 agent microharness：人发的消息只是往思想流里塞一条 observation | 它把前缀缓存当一等公民（见第 7 节）；它的块是"按行号对齐的滑窗＋无限增长的日志投影"，我们是"写满 2 万 token 就切" |
| [OptMem](https://github.com/VictorTaelin/OptMem) 2.3k | 426 token 提示词 ＋ 一个无依赖脚本：定宽日志 ＋ 二叉摘要树，`memo wake` 输出不超过 96 行 | 它是我们这套东西的最小化版本，没有常驻循环；但它的粒度是连续曲线（见第 7 节），我们是固定 4 层 |

能直接借的四处：

1. **按路径回忆**（agent-memory）`[官方文档]`：召回不返回正文，只给"路径＋一句摘要＋锚点＋分"，
   再由调用方决定读多深（outline / abstract / full），原文另走一条 trace。
   这一条我们**已经有一半** `[源码]`：`recall` 只回 id、名字、日期（旧入口还带回哪次聊天、
   连接数）；`recollect` 才按一条 id 把当时写成第一人称回忆（见 `memory_v2/prompts/event-system.txt`）。
   差的是第三层——它有一档"退回原文核对"，我们没有这个工具：重写的回忆里若数字或原话错了，
   无从对证（材料还在库里——`loop/` 是 note，旧事件是场次记录——只是没暴露给模型）。
2. **权重结算**（agent-memory）`[官方文档]`：读的时候只写访问日志，不改记忆；睡眠期统一结算
   `weight += 0.5 × min(reads, 3)`，闲置 30 天 `-0.1`，夹在 `[0.05, 5]`。
   我们的事件有 `access`：取用一次 +0.1、按天 ×0.9，激活时乘 `1 + 0.1 × access`；band 只有
   `band_decay = 0.8`。差的是"攒到睡眠期再结算"——我们是取用时立刻加，且只影响排序的一成。
3. **先分段再压缩**（nemori）`[官方文档]`：不让模型按固定字数切，而是让它按话题边界返回消息下标，
   每段生成一条叙事；相对时间强制换算成绝对日期、精确到小时。
   我们按 20k token 切块、一块一条摘要——一个块里有两件事，就会被压进同一条。
4. **重要度与反思**（[generative_agents](https://github.com/joonspk-research/generative_agents)，
   Stanford 的 Smallville）`[源码]`：检索分 = `0.5×新近 + 3×相关性 + 2×重要度`
   （`retrieve.py` 里 `gw = [0.5, 3, 2]`），新近按条目在时间线上的位置做几何衰减；
   取用一次就更新 `last_accessed`——被想起的记得更牢；
   重要度累计花掉 150 的预算，就触发一次"反思"，把零散事实写成更高一层的判断（`reflect.py`）。
   我们的 band 只有"第几层 × 0.8"；事件另有 `consolidation`（重放给出）与 `access` 两处微调，
   但没有"反思"这个动作。
   而反思正是"性格随时间变"的来源——这是我们和它最大的一处结构差。

另外 claude-mem 的**预算适配器**值得记一笔 `[官方文档]`：先整块渲染再量长，超过上限就按固定顺序
降级重渲染（砍全文叙事 → 砍上一条摘要 → 会话数减半 → 条数减半），整项丢、绝不截半。
它治的是"整段放不下"这件事——我们压 band 时也会遇到（一条摘要塞不进一层）。

## 4. 记忆层平台那三个

| 仓库 | 一句话 | 能借的 |
|---|---|---|
| [memobase](https://github.com/memodb-io/memobase) 2.9k | 用户画像式长期记忆服务，停更约 9 个月 | 每次压缩落一条不可变事件（摘要＋标签＋画像增量），当前状态另存槽位：**时间线与现状分离** |
| [MemOS](https://github.com/MemTensor/MemOS) 12k | 把记忆做成"操作系统"，有 DSH 本地插件 | 只在轮次开始注入、绝不在工具调用中途插记忆；配硬截止与降级包 |
| [powercontext](https://github.com/oceanbase/powercontext) 1.4k | 把决策/约束存成带 revision 的 Artifact | 软遗忘（状态位，历史保留可恢复）＋按 section 配预算；"空"是合法结果 |

我们天然占了 powercontext 那条便宜：源头消息一直在 SQLite 里，band 压坏了可以重压一次。
真正缺的是"重压"这个动作没有入口——网页上现在只有删除记录，没有重新生成的按钮。

| [alicization](https://github.com/TouHouQing/alicization) | 17 | 议程要"阈值 AND 硬条件"同时满足才点燃；权重 EWMA 0.72/0.28 防抖 |
| [dayflow](https://github.com/0xblewalker/dayflow) | 20 | 纯缓存形状的样本（见第 7 节） |

Miru 的时间面是现成的模板 `[官方文档]`：每步上下文头里固定给 `now`、`daypart`、
`distances`（距上次用户消息／上次自己回复／上次主动各多久）、`activity`
（活跃窗口取最近 7 天首末条消息的中位数，不硬编码作息）。
它的开口有四层硬地板：正在对话时不评估、60 秒评估节流、5 分钟发送冷却、睡眠窗口；
一次调用同时产出"内心"、`speak_intent` 与 `wait_minutes`——下次什么时候再看，由模型自己定。

对照我们：`date.txt` 只给日期，`wait` 只能等固定时间或收到消息，`watchdog_idle` 是"连续 N 步
没有外部输入就问一句还在做事吗"。**我们有计时器，没有闸门。**

## 6. 主动性的时机问题

`awesome-proactive-agents` 把这件事写成一条不等式 `[二手]`：

```
intervene  ⇔  E[好处] − E[打扰的代价] > θ
```

它引的三条结论对我们最扎眼 `[二手]`（均为该清单转述的论文，我没有读原文）：

- **模型是时间盲的**：即使把时间戳直接给它，判定"该不该动手"的对齐率也没有一个模型超过 65%；
  所以"加个时间戳"不够，得给相对时长与规则。
- 2026 年三篇独立工作都收敛到"**便宜的闸门 ＋ 贵的主演**"：先用一个小模型或规则判断，
  过了才让主模型动。我们反过来——每个 tick 都是主模型。
- **打扰的代价是路径依赖的**：两小时内连着八条之后，用户对下一条的接受度减半以上。

⇒ 我们的日 token 上限是"钱"的上限，不是"打扰"的上限。

## 7. 上下文形状与缓存

我们的排布其实已经对了：sink ＋ band 在前（稳定），块在后（每步追加），
`usage` 里也已经在记 `prompt_cache_hit_tokens`。但没有任何一条纪律保证它不变形。

| 项目 | 做法 `[官方文档]` | 对我们的意思 |
|---|---|---|
| dayflow | focused 10K → activation 26K；涨到 26K 才轮转，且本轮释放不足 2000 token 就不转；轮转后尾巴夹在 3000–5000 | 我们的 band 压缩没有"最小释放量"，压一次可能只省 300 token |
| dayflow | 投影形状固定（`<context>` 胶囊 ＋ 一句固定 ack ＋ 尾巴），轮转之间前缀逐字不变 | 我们的 `today` 在 sink 里每天变一次，可接受；**"现在几点"绝不能进 sink** |
| 心潮·念 | 信封硬预算 2200 token、TTL 15 分钟、段带 `ttl` 标签，稳定人格不进信封 | 稳定与易变要分层，我们目前只有"块"这一层 |
| alicization | 3200 token = SOUL 25% / memory 25% / 当前轮 50% | 我们的 `band_budget` 是绝对数，没有"占比"视角 |
| MemOS | 只在轮次开始注入，硬截止 3 秒，坏 JSON 退化为空包 | 我们的 recall 失败会怎样，没定过 |
| pawwake | 摘要区是"尾部追加"的 content block，旧摘要 block 仍命中缓存；区上限 8000 字符，超了把最旧几段折叠、固定留最近 2 段 | 我们每次压缩都**重写**一段 band，那一段的前缀就整段变了；追加比重写省 |
| headlong | 块边界按行号对齐，band 边界与尾部窗口在同一次移动里改，"共用一次缓存重置"；最新的 W 个块给大字节上限，更老的截到 2048 字节 | 我们切块按估算的 token，时机任意；压缩与切块也没绑在一起 |
| OptMem | 保留一整块的条件是 `s ≤ α·(T−lo)`（s 块大小、T 总条数、lo 起点），α 二分到刚好填满窗口 | 我们是固定 4 层 × 0.8，层数是手填的，不是从预算反解出来的 |

## 8. 借不了的，和为什么

- **mem0 / zep / Letta 那一整支**（`long-term-memory` 的前几名）：他们解决的是"跨会话记住事实、
  需要时检索出来"。我们不需要在每步检索——记忆就在上下文里连续排着，检索只是辅助。
  照他们的结构做，会把"在场"退化成"问答"。
- **网关与钩子形态**（kiwi-mem / MemOS / claude-mem）：宿主是别人的会话，所以只能挂钩子。
  宿主是我们自己，多这一层只会多一处失败点。
- **多用户画像、情绪状态机、人格蒸馏**（memobase / Mirrai）：单人单一心智不需要租户；
  zifamem 的论文说"在已有结构化记忆之后，额外的情绪状态机带来不了可测增益" `[官方文档]`——
  这条反面证据值得记住，别把情绪做成第二个状态机。
- **Markdown 为真源**（agent-memory / fish-memory）：他们要让文件可读可 diff；我们是 SQLite 单写，
  改这一条会把写路径拆成两半。
- **摘要只写增量**（nemori 的 Predict–Calibrate）：它压的是**累积式**摘要，每一版都要重新覆盖
  过去，所以有重复可去、也值得去。我们的 band 是"一块一条"，段与段在时间上不重叠，压缩模型
  根本看不到已有摘要——没有增量可写；真按 diff 写，最旧一段被挤掉后，后面几段的"相比之前"
  就失去参照，四档阶梯也失去可截的内容。它那一步"抽取新事实"在我们这里对应 `remember`
  写 note，不对应 band 压缩。
- **原文召回派**（Paramecium，来自清单 `[二手]`）：它们认为"摘要即失真"，只召回原文。
  这正好是我们的反面假设，可以当作压力测试，不是可借的东西。

## 9. 落到 `loop/` 的候选

按"改动大小 ÷ 可能收益"排，每条都指到具体位置：

| 候选 | 借自 | 代价 | 落到哪 |
|---|---|---|---|
| 时间面：`now`、距上次对方说话多久、距上次自己开口多久、活跃窗口 | Miru、time-anchor | 小：渲染一行，放块尾（不进 sink，保前缀） | `context.py` 的块渲染 ＋ `date.txt` 改写 |
| 压缩设最小释放量（省不到 N token 就不压） | dayflow | 小：一个参数 | `config.py` ＋ `_compress_if_needed` |
| 重压：按时间区间把旧 band 从源头再压一遍 | powercontext 的 revision 思路 | 中：网页加一个动作，只写库里已有数据 | `store.py` ＋ `web.py` |
| 摘要追加而不是重写 band | pawwake | 中：改压缩的写库方式，band 允许多段追加与折叠 | `compress.py` ＋ `store.py` |
| 按事件 id 取回原始 note（旧事件才是对话原文），不经编写 | agent-memory 的 trace | 小：`read/search.py` 的 `expand()` 已经会展开，只差一个只读工具 | `memory_bridge.py` |
| 记忆带重要度，累计到一个预算就写一条"反思" | generative_agents | 大：要新字段、新动作，还要定"谁评重要度、多久反思一次" | `memory_bridge.py` ＋ `compress.py` |
| 睡觉时整理（park 期间做一次：合并重复、结算权重、重写 persona 的差异） | agent-memory | 中：要新状态与配额，且必须可回滚 | `driver.py` 的 `_park` 之后 |
| 开口闸门（强度阈值 ＋ 冷却 ＋ 日配额 ＋ "上次开口没人理就更久"） | 心潮·念、Miru、alicization、revive-companion | 大：要多一个轻量判定与一份"想说的话"状态。可抄的数值：`P=1−e^(−λt)`、λ=0.15、命中但没发出仍继续累积、只有真发出才归零；headlong 的退避是 `5·2^(n−1)` 封顶 300 秒、连续 3 次空唤醒就停 | `driver.py` 的 nudge 附近，替掉 `watchdog_idle` |
| band 衰减换成"半衰期 ＋ 召回加成" | kiwi-mem、zifamem | 中：会动 band 的排序与淘汰，需要实测才知道好不好 | `context.py` 的 band 淘汰 |

我的判断 `[推断]`：排在前三条的都不用新状态，是"改提示词＋加参数"的量级，
补的是**时间感与压缩质量**；而真正缺的那一块——没人说话时它凭什么开口——只有倒数第二条那一项，
要新增一份"想说的话"的状态，改提示词糊不过去。

## 10. 还没答案的

- **0.8 的时间衰减 vs 热度模型**：我们按"第几层"衰减，kiwi-mem 按"多久没被想起"衰减。
  两者在长跑里会分叉（一条一年前但很重的事，在我们的 band 里必然沉底）。没有证据说哪个对。
- **回忆是重写还是原文**：我们选了重写；Paramecium 选了原文。这条分歧没有实验能判。
- **固定 4 层 vs 连续粒度**：OptMem 用 `s ≤ α·(T−lo)` 让粒度随年龄线性放宽，层数由预算反解；
  我们的 4 层和 0.8 是手填的。层数是不是从长跑里长出来的，没有证据。
- **打扰的代价**：所有材料都在说"别太频繁"，但没有一个给出适合单人长跑的 θ。
  我们的日上限只约束钱。这一条只能自己长跑试出来。

## 11. 顺带一个观察

按 `ai-companion` 扫下来，绝大多数项目的"记忆"是**事实卡**（身高、喜好、纪念日）＋ 每日摘要，
没有分层、没有衰减、没有重写。也就是说：**我们不是"做得更好一点的同类"，我们是另一条路线**。
这一点对仓库描述和 README 的写法有直接影响——我们不该拿"长期记忆"去和别人比功能，
该比的是"它记得的是不是它自己经历过的那段"。
