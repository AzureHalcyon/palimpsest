## 0 一句话

她能放下一件"将来的事"——**一句话 + 一个时刻**；到点那句话作为一条**进件**回到记录里，别的什么都不做：
不起第二个执行路径、不写假对话、不替她决定做不做。

---

## 1 缺什么

现在的时间感只有末尾一行墙钟（知道隔了多久）。`wait` 能等到某个时刻，但**它等的是这一步**：

1. **挂着 wait 的意图会丢。** 她说"明天再问你结果"，然后调 `wait(until="明天 9:00")`；
   今晚只要有人说话，她就醒了，那个"明天"就没了——没有地方记着。
2. **只能等一件，只能等这一次。** 两个念头（"三点提醒我"和"晚上问他"）没法同时存在。
3. **跨重启、跨场不成立。** 重启后块里挂着没有结果的 `wait` 会接着等，但"要把这件事记起来"不是 `wait` 的一部分。

理想里对得上的三条：[`理想.md`](理想.md) 的「时间感」「可以主动」「去年今日、上次没说完的」。
它要的不是任务系统，是**前瞻记忆**：将来的我该记得这件事。

---

## 2 边界：它是闹钟，不是任务系统

| 它做 | 它不做 |
|---|---|
| 存一句话 + 一个时刻 | 不做 cron 表达式、不做重复规则（第一版） |
| 到点把这句话写成一条进件 | 不因到点起子会话 / 二次 agent run |
| 由她（或人）决定做不做、什么时候做 | 不做优先级、依赖、看板、完成率 |
| 响了就响一次 | 不因"没做"反复提醒、不催 |

**和「把空闲改写成任务」的区别**（[`理想.md`](理想.md) 第一条滑点）：闹钟不要求产出、不排期、不需要交付。
它只是把"将来该想起的事"还给她；做不做属于她。

---

## 3 单位与名字

术语表加一条：**未来件** —— 一行"将来的事"：`note`（一句话）＋ `due_at`（UTC 时刻）＋ 谁放的 ＋ 回给谁。
和 **进件**（`inbox`，外面来的）分开：进件是"已经到了的"，未来件是"还没到的"。

到点之后未来件**变成一条进件**（`kind='due'`），从此走已有的读取、对账、trim、渲染，不再特殊。

---

## 4 数据

一张新表（与 `inbox` / `chats` 并列，`loop/store.py` 的 schema 里加）：

```sql
CREATE TABLE IF NOT EXISTS future (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    due_at     REAL NOT NULL,              -- UTC epoch，和 wall clock 同一个钟
    note       TEXT NOT NULL DEFAULT '',   -- 一句话，到点原样用它
    status     TEXT NOT NULL DEFAULT 'pending',  -- pending | fired | done
    fired_at   REAL NOT NULL DEFAULT 0,    -- 0 = 还没响过
    chat_id    TEXT NOT NULL DEFAULT '',   -- 回给哪个会话
    chat_name  TEXT NOT NULL DEFAULT '',
    source     TEXT NOT NULL DEFAULT '',   -- 谁放的：tool / 以后的 web
    sender_id  TEXT NOT NULL DEFAULT '',
    sender_name TEXT NOT NULL DEFAULT '',
    meta       TEXT NOT NULL DEFAULT '{}'  -- 留位：将来挂 event_id / recur
);
```

**为什么不复用 `inbox` 加一列 `due_at`**：那样"未读数"和 `trim_inbox` 都要改成"排除没到点的"，
而 `inbox` 的语义是"外面进来的东西"，混进去之后 `wake` 那句"N 条没看的消息"会失真。
新表只多一次 insert + 一次 update，比改四处 SQL 干净。

**为什么 `note` 原样用、到点不重新生成**：这一行是**她当时怎么想的**，不是现在对她的转述。
重新生成等于让第二个作者介入（[`解构与重建.md`](解构与重建.md) §1 第 3 条同一个理由）。

---

## 5 到点怎么醒来：和 `wait` 共用一口钟

**不另起线程、不另起定时器**。`wait` 现在是在循环里轮询/睡到 deadline（`driver.py` 的 `_wait` / `_breathe`）；
这里只把 deadline 换成"两个里更早的那个"：

```
这一步的 deadline = min(wait 的 until, 最近的 pending due_at)
```

醒来后按顺序做判断：

1. 有进件？（`_drain_inbox` 非空）→ 醒，正常处理；
2. 有到点的未来件？（`due_at <= now`）→ **先落成进件**，再走 1；
3. 到了 `until` → 回"等到 14:30，到点了，没等到"（现有文案不变）。

**落成进件的动作**（幂等，一条 SQL 判行数）：

```
UPDATE future SET status='fired', fired_at=now WHERE id=? AND status='pending'
-- rowcount==1 才 INSERT 进件
```

进件写：`kind='due'`、`direct=1`、`source='闹钟'`、`text=` 拼好的那一行、`chat_id` 照抄。
用 `direct=1` 是因为它**不算外部消息**：不该进"N 条没看的消息"那个计数，也不需要她再 `messages` 去取。

**记录里长什么样**（进件渲染的既有格式，`_inbox_entry` 那条路）：

```
提醒：明天问一下他面试结果（9 月 12 日 09:00 设的，还有 3 分钟到点）
```

迟到就换后半句：`（晚了 3 小时 12 分）`。

---

## 6 迟到、过期、停机

- **停机跨过了 due_at**：恢复后第一步补一次，并在那一行写"晚了多久"。**补一次，不补一串**：
  同一步最多补 `future_batch`（默认 3）条，剩下的留到下一步。
- **超过 `future_late_grace`（默认 24 小时）**：不补，只把状态改成 `done` 并留一行 log
  （"有一条提醒过期了：…"）。理由：隔了一天半的"提醒我三点开会"已经不是提醒了，说出来只会让她困惑。
- **迟到很久但不超 grace**：照补，但**不说"现在正好三点"**——那是撒谎。

## 7 谁放：第一版只有她自己

三个工具（工具说明在 `loop/prompts/tools/`，一份一个，和 `wait.txt` 同规格）：

| 工具 | 参数 | 说明 |
|---|---|---|
| `future` | `note`, `at` | 放一件。`at` 与 `wait(until=…)` **同一个解析器**（`driver.py` 的 `parse_until`：`10m` / `90s` / `2h` / `14:30`），不新增时间语法 |
| `future_list` | — | 还没到点的，按时间排；已响没了的也列，标"响过了" |
| `future_done` | `id`, `note`（可选） | 了了 / 不做了。`note` 写为什么——这一句是她自己的记录 |

三条硬规矩：

1. **不自动 `done`。** `fired` 只表示"提醒已经进记录"，是否算完事由她说。否则她会以为自己已经做完了。
2. **过去时间直接拒。** `at` 解析出来 `<= now` 就回"这个时刻已经过去了"，不自动立刻触发
   （那会让她把"现在"当成"以后"来用，写出一堆马上响的闹钟）。
3. **满额拒绝要带清单。** pending 到 `future_max_pending`（默认 32）就拒，并把当前清单回给她
   （id、note、还有多久）——她要能自己处理，而不是被一句"太多了"卡住。

**第一版不给人留入口**：人想让她记，直接说一句"明天提醒我问他结果"，她会自己放。
`source` 列留着，将来网页/命令行要写同一张表时不用改结构。

---

## 8 边界与上限

| 参数 | 初值 | 管什么 |
|---|---|---|
| `future_max_pending` | 32 | pending 上限（到点未响的都算） |
| `future_late_grace` | 24h | 超过就不补，只记一行过期 |
| `future_batch` | 3 | 一步最多补几条 |
| `future_keep` | 2 | 记录里最多留最近几条提醒 |
| `future_note_max` | 200 字 | 一条 note 的上限 |

另外两条从 `run` 那里借来的：`note` 里点到凭证 / 密钥 / `.ssh` 就拒；`note` 不许出现另一件事的完整正文
（它就是一句话，不是便条本）。

---

## 9 注入与缓存

- 提醒**只进记录末尾那一帧**，绝不进 sink（sink 每步缓存，进去一次整段前缀作废）——
  和墙钟、watchdog、`ask.txt` 同一类。
- 记录里只留最近 `future_keep`（默认 2）条；更早的不再渲染（watchdog 已有先例）。
- 已经 `fired` 的不重复响：检查条件只看 `status='pending'`，幂等靠那条 SQL 的 rowcount。

---

## 10 状态机

```
pending ──到点──> fired ──future_done──> done
   └──────────future_done（还没到点就撤）──────┘
```

`fired_at` 记"响过没有"，所以 `done` 有两种含义（做了 / 撤了），查得出来：
`fired_at=0` 就是没响就撤了。

## 12 自检与量具

`loop/selfcheck.py` 加一组 `check_future`，五条：

1. 放一条 2 秒后的 → `wait` 醒来 → 记录里**出现且只出现一次**；
2. 放一条过去的 → 被拒，文案说出"已经过去了"；
3. pending 满 → 被拒且清单里能看见已有的；
4. 改 `due_at` 到 10 分钟前（模拟停机跨点）→ 补一次，且那一行带"晚了 10 分钟"；
5. 改 `due_at` 到 30 小时前 → 不补，状态变 `done`。

量具（网页，只报警不裁决）：pending 数、最老一条等了多久、平均迟到、过期丢弃数。

## 13 不做什么

| 不做 | 为什么 |
|---|---|
| cron 表达式 / 每天八点 | 会立刻引出"错过补几次""跨时区""夏令时"三串问题；先做一次性的，重复等真需要（[`决策记录.md`](决策记录.md) 里"不为还没出现的情况加机制"） |
| 到点起一个子会话 / 二次 agent run（AstrBot 的 `active_agent` 那样） | 本仓的循环是唯一的执行体；多开一条就破了单写者 |
| 把执行结果写成假对话回灌历史（AstrBot 的 `summary_note`） | 原文只读；历史里不能出现她没说过的话 |
| 到点自动 `wait` / 自动替她决定做不做 | 2026-10-25「停是她自己的动作」那条的同一件事 |
| 给 future 加优先级、标签、依赖 | 那是任务系统，不是闹钟 |
| 到点重新生成 note | 那是让第二个作者介入她的记录 |

---

## 14 待决

- **重复**（每天 / 每周）：要不要，什么时候要。加的时候只需多一列 `recur` + 响过之后重算 `due_at`，
  但"错过三天要不要补三天"必须一起定。
- **能不能给别人放**（现在钉死在会话，不是钉在人）：群聊里"提醒他"这种用例要不要支持。
- **`future_late_grace` 24 小时**是否合适——按"提醒"语义估的，没有实测。
- **时区**：现在按本机。远程部署后 `at` 用谁的钟（镜像配置 vs 每个会话一个时区），要先定，
  否则 `wait` 与 `future` 会一起偏。
- 网页要不要给人用的入口（现在只给她）。
